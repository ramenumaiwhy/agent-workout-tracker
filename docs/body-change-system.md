# 身体変化を分析する仕組み

## 結論

この仕組みの目的は、記録を増やすことではありません。

食事、ジム頻度、InBody、体重、セット実績を時間軸で結び、次の問いへ答えます。

- 何が変わったか。
- 変化の前に、何を意図して変えたか。
- その変更を、実際にどの程度実行したか。
- 変化に関係した可能性がある要因は何か。
- 変わらなかった場合、どの説明が考えられるか。
- 次に一つだけ確認することは何か。

個別の記録moduleは小さく保ちます。複数の記録を同じDBへ統合しません。身体変化エージェントが各moduleのinterfaceから事実を取得し、身体変化文脈を作ります。

## 現在の記録

### 食事・身体・ジム

Hermesは`meal-tracker`のローカルCLIとSQLiteを使います。現在のSQLiteには次のtableがあります。

- `food_items`: 食品の基準値と出典
- `meal_entries`: 実際に食べた品目と、その時点のkcal及びPFCの写し
- `body_measurements`: InBody CSVから取り込んだ身体計測
- `gym_visits`: ジムへ行った実績

`meal_entries`は、食べた時刻と報告時刻を分けて保存できます。報告原文、日付を決めた根拠、栄養値の出典も保存できます。食品の基準値を後で直しても、過去の食事実績は変わりません。

現在の分析は、日別と直近期間のkcal及びPFC、InBodyの前回差と傾向、ジムの週別頻度を扱います。判定条件は`meal-tracker`内にあります。人向けの`からだログ`は状態確認用です。助言はHermesが返します。

現時点では、次の情報がありません。

- 増量、減量、維持のどれを目指す期間か。
- いつ、何を意図して変えたか。
- 変更によって何が起きると予想したか。
- 食事、トレーニング、身体計測を機械向けにまとめて取得する安定したinterface

### 筋トレ

`agent-workout-tracker`は、セット実績を独立したSQLiteへ保存します。記録、訂正、取消、種目登録を一つの`record` interfaceに隠します。`context`は、現在と直近のトレーニング文脈をJSONで返します。

筋トレ記録は、身体変化を直接説明しません。次の事実を供給します。

- ジムへ行っただけでなく、どの負荷を実行したか。
- 同じ種目の重量と回数が変化したか。
- トレーニング刺激が維持、増加又は低下した可能性があるか。

## 言葉

**身体変化エージェント**:
複数の記録moduleから事実を取得し、変化と非変化を分析するAIエージェントです。元の記録を所有しません。
_Avoid_: ヘッド、統合DB、司令塔

**身体変化文脈**:
身体変化エージェントへ渡す、対象期間の目的、変更記録、実行実績、結果、データ品質の要約です。元の記録から都度作る派生情報です。
_Avoid_: 全データ、プロンプト、共有DB

**体づくり期間**:
増量、減量又は維持など、一つの目的を持つ期間です。開始日と終了日又は継続中の状態を持ちます。
_Avoid_: モード、フェーズ

**変更記録**:
利用者が結果を変える意図で、食事又はトレーニングの方針を変えた事実です。開始日、変更内容、意図、期待する変化を含みます。
_Avoid_: 設定、メモ、施策ログ

**実行実績**:
変更した方針を、実際にどの程度実行したかを示す事実です。食事実績、ジム実績及びセット実績から作ります。
_Avoid_: 頑張り、遵守スコア

**結果指標**:
身体又はパフォーマンスの変化を見る値です。体重、InBody、主要種目の重量及び回数などが該当します。
_Avoid_: 成果、効果

**要因候補**:
観測した変化又は非変化に関係した可能性がある項目です。個人の観測データだけでは原因を証明できないため、原因とは呼びません。
_Avoid_: 原因、真因

**次の確認**:
要因候補を区別するために、次の期間で一つだけ変えるか、追加で測る項目です。
_Avoid_: AIの処方、自動改善

## 全体構造

```text
利用者
  │
  ├─ 食事の報告 ─────▶ 食事・身体記録 module ───▶ SQLite
  ├─ InBody CSV ─────▶          │
  ├─ ジム実績 ───────▶          │
  ├─ セット実績 ─────▶ 筋トレ記録 module ───────▶ SQLite
  └─ 方針の変更 ─────▶ 変更記録 module ─────────▶ ローカル保存
                              │
                    各moduleの読み取りinterface
                              │
                              ▼
                       身体変化文脈
                              │
                              ▼
                     身体変化エージェント
                              │
             ┌────────────────┼────────────────┐
             ▼                ▼                ▼
          観測事実          要因候補         次の確認
```

身体変化エージェントはSQLiteを直接読みません。各記録moduleが正規化、訂正、出典、欠測及び集計の複雑さをinterfaceの内側へ隠します。

## 身体変化文脈

身体変化文脈は、全ての生データを含めません。分析に必要な事実と、その根拠への参照だけを含めます。

```text
文脈情報
  schema_version
  generated_at
  timezone

対象期間
  開始日
  終了日又は継続中

体づくり期間
  目的: 増量 | 減量 | 維持
  判断に使う結果指標

変更記録
  開始日
  対象: 食事 | トレーニング | その他
  変更前
  変更後
  意図
  期待する変化

実行実績
  食事の記録日数と期間集計
  ジム頻度
  主要種目のセット実績と推移

結果指標
  体重の傾向
  InBodyの傾向
  主要種目の推移

データ品質
  欠測日
  推定した食事
  測定間隔
  比較条件の違い

根拠参照
  元の記録module
  記録ID又は対象期間
```

身体変化文脈は、保存先の共通形式ではありません。身体変化エージェントの読み取りinterfaceです。各moduleのSQLiteは引き続き正本です。欠測と数値の0は区別します。単位は項目名又は値へ明示します。任意の信頼度を数値で作らず、欠測、推定又は測定条件を事実として返します。

## 身体変化エージェントの出力

出力は次の順に固定します。

1. **観測事実**: 記録から直接確認できること
2. **要因候補**: 時期と実行実績が整合する候補
3. **判断できないこと**: 欠測、測定誤差、同時変更など
4. **次の確認**: 次の期間で一つだけ確認すること

例:

```text
観測事実:
摂取kcalの期間平均は増えた。体重は横ばいだった。主要種目の重量も横ばいだった。

要因候補:
摂取量の変更幅が小さかった可能性がある。記録がない日もあるため、実際の期間平均は確定できない。

判断できないこと:
食事とトレーニングを同じ日に変更したため、個別の影響は区別できない。

次の確認:
次の2週間はトレーニング方針を変えず、食事記録の欠測を減らす。
```

身体変化エージェントは「原因が確定した」と言いません。医療判断も行いません。データが不足する場合は、分析を保留します。

## Moduleの責務

### 記録module

- 自分が担当する事実だけを保存する。
- 報告時刻と実施又は測定時刻を分ける。
- 訂正後も元の報告を確認できる状態にする。
- 同じ依頼の再送で記録を増やさない。
- 機械向けの安定した読み取りinterfaceを返す。
- 事実と、担当領域内の決定的な集計を返す。
- 利用者ごとの方針又は複数領域を使う助言を返さない。
- 他の記録moduleを直接参照しない。
- 身体全体の原因分析を行わない。

### 身体変化エージェント

- 各moduleのinterfaceだけを使う。
- 同じ期間へそろえて比較する。
- 事実、要因候補、判断不能を分ける。
- 変更記録がない場合は、後から意図を作らない。
- 複数の変更が重なった場合は、要因を特定できないと示す。
- 次の確認は一つに絞る。
- 元の記録を直接変更しない。

## 最小の追加設計

最初に必要な追加は二つだけです。

1. `meal-tracker`へ、対象期間の食事、身体及びジムの事実をJSONで返す読み取りinterfaceを追加する。
2. 体づくり期間と変更記録だけを保存する、小さい変更記録moduleを分析側へ追加する。

身体変化エージェントは、既存の筋トレ`context`、新しい食事・身体`context`、変更記録`context`を取得します。その結果から身体変化文脈を組み立てます。

変更記録moduleのために、別repo、別プロセス又は公開interfaceを先に作りません。最初は身体変化エージェントと同じ実装内に置きます。二つ目の利用元が必要になった時点で、独立したseamを作ります。

最初は次を作りません。

- 共通DB
- イベント基盤
- ベクトルDB
- 機械学習モデル
- 自動的な因果判定
- 全記録moduleを包む汎用framework
- 食事、身体、ジムのrepo分割

`meal-tracker`は現在一つの実装に三種類の記録を持ちます。今すぐ分割しても利用上の価値は増えません。まず安定した読み取りinterfaceを作ります。独立した変更理由又は別の利用者が必要になった時点で、seamを再評価します。

## 最初の検証

最初の4週間は、現在の記録へセット実績と変更記録を追加します。評価することは一つです。

> 身体変化エージェントが、記録を追加したことで、以前より有用な次の判断を返せたか。

分析によって判断が変わらない場合は、記録項目又は分析機能を増やしません。
